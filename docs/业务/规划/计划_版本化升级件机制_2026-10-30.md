# 计划书：版本化升级件机制（Migration）——种子冲突语义缺陷第二步

- **状态**：**待评审（本计划不出码）**；2026-10-30 起草
- **来源**：本仓 `docs/上报_种子冲突语义缺陷_2026-10-30.md` §3/§4 第二步（用户终裁：种子一律"缺行才插"，结构演进走升级件）
- **前置**：第一步已落码＝种子执行统一"按主键缺行插入、已有跳过"（`SqlSugarSetup.StoreSeedData` 单点，主库/租户库同路径）
- **结论先行**：本机制把"结构演进"从**每次启动的隐式 upsert**改成**有编号、显式执行、可审计、升级前有备份、失败即停**的迁移流程；核心风险不在技术实现，而在**存量库的基线登记**与**失败即停和现有启动降级口径的冲突**（见 §7 决策点 D2/D4，需评审拍板）

## 1. 目标与非目标

### 1.1 目标

1. 提供**版本表**：每个库（主库/各租户库）各自记录"已应用到第几版"。
2. 提供**有序脚本**：`Migrations/` 下按版本号升序执行，版本号全局唯一、脚本内容有校验和。
3. **升级前备份**：执行前对被影响表（或整库）留可恢复备份点，备份失败则拒绝升级。
4. **失败即停**：单脚本单事务，失败回滚该脚本并中止启动/升级流程；不跳过、不降级继续。
5. **可审计**：每脚本执行留版本行（版本/描述/校验和/开始结束时间/耗时/执行者实例）＋结构化日志。
6. **尊重运行时差异**：提供"仅当库值仍等于旧默认值时才更新"的迁移帮助 API，避免迁移脚本二次踩中"覆写用户修改"的老坑。

### 1.2 非目标（明确不做）

- **不做 ORM/表结构迁移**：表结构继续由 `CodeFirst.InitTables`（`[IncreTable]` 增量）负责；升级件只做**数据演进**（默认值变化、树重挂、授权行补齐、字段回填、行删除等）与必要的一次性 SQL。
- **不做自动回滚/Down 脚本**：删除型/破坏型回滚易丢数据，回滚＝备份恢复＋人工；版本行只增不删（审计需要）。
- **不恢复 per-seed 覆写通道**：上报件 §4.3 已否（Conflict 枚举/按表硬编码特例）；本机制是唯一的结构演进入口。
- **不引入第三方迁移库**（EF Migrations/FluentMigrator 等）：与"零 Furion/最小依赖"口径冲突，且本仓已自建启动骨架，自研 runner 成本可控（约 300 行量级）。
- **不自动扫全部租户库**：启动期只升级主库；租户库升级走既有 `initDb` 管理端点/运维脚本显式触发（避免启动时长随租户数放大）。

## 3. 机制设计（拟）

### 3.1 版本表

拟新增实体 `SysMigration`（`[IncreTable]`，表 `sys_migration`，主库与每个租户库各一份）：

| 列 | 类型 | 说明 |
|---|---|---|
| `Id` | bigint PK | 雪花（沿用 `EntityBase` 口径） |
| `Version` | varchar(64) | 脚本版本号（唯一索引；`yyyyMMdd_NN` 形式） |
| `Description` | varchar(256) | 人读描述 |
| `Checksum` | varchar(64) | 脚本内容 SHA-256 前 16 字节 hex（防"已应用脚本被偷改"） |
| `Baseline` | bool | 是否为基线登记行（§3.7） |
| `AppliedAt` | timestamptz | 应用时刻 |
| `DurationMs` | int | 执行耗时 |
| `InstanceToken` | varchar(128) | 执行实例标识（`StartupSchemaInitializer` 已有 instanceToken 口径，便于多实例归因） |

- 唯一性：`Version` 普通唯一索引（不建部分唯一索引——版本表不软删，保持强约束）。
- 不继承 `EntityTenant`：租户库中它属于"库元数据"，不参与行级租户过滤；按库分表自然隔离。

### 3.2 脚本载体与发现

- 落点：`src/Core/Migrations/`（框架脚本）＋将来业务侧 `src/Business/Migrations/`（扫描程序集与种子同口径传 Core＋Business）。
- 形式：**编译进程序集的 C# 类型**（非运行时读 .sql 文件），接口拟为：

```csharp
public interface IMigration
{
    string Version { get; }          // 例:"20261101_01";全局唯一,启动扫描重复即 fail-loud
    string Description { get; }      // 人读
    IReadOnlyList<string> AffectedTables { get; } // 备份范围声明(表级快照,见 §3.6)
    Task UpAsync(ISqlSugarClient db); // 库内 DML/一次性 SQL;禁止 DDL(表结构归 CodeFirst)
}
```

- WHY C# 而非 SQL 文件：① 升级件内需要"仅当仍等于旧默认值才更新"的分支与租户/多库路由（拿得到 `ISqlSugarClient`）；② 编译期即校验类型与引用，无"部署漏拷文件"风险；③ 与既有 `[IncreSeed]` 反射扫描机制同构，学习成本最低。
- 排序：`Version` 字符串序（固定 `yyyyMMdd_NN` 即字典序=时间序）。**不做**按类型名/反射顺序的隐式排序。
- 校验和：取 `Version + Description + AffectedTables + 方法体 IL 的 SHA-256`（实现上取 `MethodBody.GetILAsByteArray()` 即可，避免手工维护常量）。

### 3.3 执行位置与次序

拟定为：

```
HealColumnCase → InitTables → InitSeeds(命令式) → InitSeedData(声明式,缺行插入) → RunMigrations(新) → 汇总日志
```

- **为什么不放在种子之前**：升级件常需引用"本版本新增的种子行"（如新菜单按钮的行、授权派生目标）。种子先跑可保证基础行存在；升级件随后只做"对既有行的改造"。
- **为什么不放在建表之前**：升级件使用实体/仓储读写，必须表已存在。
- 执行点在 `StartupSchemaInitializer.RunSchemaAndSeedsAsync` 锁内（复用跨实例锁），并在版本表上加 `pg_advisory_xact_lock` 作为第二道防并发（可选，见 §7 D5）。

### 3.4 执行流程（逐脚本）

对每个库：

1. 若版本表不存在 → 由 `InitTables` 建出（`[IncreTable]`）。
2. 读取已应用 `Version` 集合与 `Checksum`。
3. 校验：已应用脚本的 checksum 与当前代码不一致 ⇒ **fail-loud 中止**（"已应用脚本被修改，禁止静默重放"）。
4. 按 `Version` 升序取未应用脚本：
   - 备份（§3.6）→ 成功才继续；
   - `db.Ado.BeginTran()` → `UpAsync` → 插入版本行 → `CommitTran()`；
   - 异常 ⇒ `RollbackTran()` → 记 `[migration] {version} FAIL {ms}` → **中止启动**（fail-fast，语义见 §7 D2）；
   - 成功 ⇒ 记 `[migration] {version} ok {ms}`。
5. 结束落汇总行：`[migration] 库={configId} 已应用 {n}/新执行 {m}/失败 {k}`（无脚本也打基线读数）。

### 3.5 幂等与"已应用"判定

- 判定单源＝版本表，不是"脚本自己猜"。脚本内部仍要求**可重入**（即使被人工重跑一次也不炸）：框架层面靠版本行挡住重复执行，脚本层面靠"条件更新/INSERT ... WHERE NOT EXISTS"兜底。
- 版本行与 DML 在同一事务：不会出现"数据改了、版本没记"的半完成态；极端情况下事务提交成功但进程在打日志前崩溃——版本行已落，下次正确跳过（日志缺失不影响正确性，只影响可观测）。

### 3.6 升级前备份

三方案对比，推荐 **B 为主 + A 可选**：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 整库 `pg_dump` | 升级前脚本调 `pg_dump -Fc` 落 `/data/backup/` | 完整、可全库恢复 | 重；依赖宿主 `pg_dump`；库大时分钟级；需额外磁盘 |
| **B 表级快照（推荐）** | `CREATE TABLE "<table>_bak_<version>" AS SELECT * FROM "<table>"` | 纯 SQL、无外部依赖、只备份被改表、秒级 | 仅覆盖 `AffectedTables` 声明的表；需清理策略 |
| C 逻辑导出 JSON | 框架读表写文件 | 无 DB 权限要求 | 恢复需自写回灌、大表内存风险 |

- 采用 B：`AffectedTables` 为空的脚本**拒绝执行**（强制声明影响面，防"忘了备份"）。
- 快照表命名：`<table>_bak_<version 去下划线>`，同库；已存在同名快照 ⇒ 视为"上次执行到一半"（版本行未落），直接复用并继续（快照内容来自升级前状态，正确）。
- 清理：保留最近 3 个版本快照，更早的由运维脚本 `scripts/migrate/prune-backups.sql` 人工执行（框架不自动删——回滚点是数据不是垃圾）。
- A 作为**发版流程**的建议动作写进运维手册（大版本升级前人工 `pg_dump`），不进框架自动流程。

### 3.7 存量库基线登记（本计划最关键的设计点）

第一步落地后，存量库上"历史种子 upsert 已完成的演进"（如 2026-09-30 菜单 Pid 重挂、配置默认值、授权行补齐）**已经发生**；若新机制把历史脚本再回放一遍，等于重放一次隐式修改，风险不可接受。

拟采用**基线登记**：

- 版本表为空且库中已存在业务数据（判定：`sys_tenant`/`sys_menu` 有行）⇒ **首启不执行任何历史脚本**，插入一行 `Baseline=true`、`Version=<当前代码脚本集最大版本>` 的基线行（若有脚本目录则一并把各脚本版本登记为已应用基线？见下）。
- 基线行语义：**"此刻库状态 = 当前代码期望状态，历史脚本一律视为已应用"**。
- 此后新增脚本（Version > 基线）才真正执行。
- 新库（空库）同样走基线登记——因为新库由**最新代码的 CodeFirst + 种子**直接建出最新状态，历史脚本无需回放。
- **代价（如实标注）**：基线登记会把"存量库实际落后于代码"的情形一并标记为已应用，掩盖差异。缓解：
  1. 上线前跑**一次性审计脚本**（只读）核对关键表/默认值/菜单树与代码期望一致，差异人工处置后再启用基线；
  2. 基线行记录 `Description="baseline@<git sha>"`，审计可追溯；
  3. 基线之后的演进全部走显式脚本，不再有"隐式补课"。

> 备选（不推荐）：脚本从零回放＋每脚本写"仅当等于旧默认值才改"的条件逻辑。它把风险转移到每个脚本的正确性上，且存量库与新库要跑不同路径——比基线登记更难验证。

### 3.8 合并策略：迁移不得二次覆写运行时修改

提供帮助类 `MigrationHelper`（形态示意）：

```csharp
// 仅当库值仍等于旧默认值时才更新;否则记日志跳过(尊重管理端/租户的运行期修改)
await db.Updateable<TSource>()
    .SetColumns(it => new TSource { ... })
    .Where(it => it.Id == id && it.Field == oldDefault)
    .ExecuteCommandAsync();
if (affected == 0) logger.LogInformation("[migration] {version} 跳过 id={id}(运行期已自定义)", ...);
```

同理提供"缺行才插"的 `EnsureRowIfMissingAsync<T>` 帮助方法（升级件里需要补行时用）。

### 3.9 多库/租户库

- 主库：启动锁内自动跑（本次范围）。
- 租户库：`InitTenantDbAsync`（管理端点 `sysTenant/initDb` 背后的建表/种子路径）同批接入"建表 → 种子 → 升级件"，按目标租户库的版本表判定；**启动期不自动遍历租户库**。
- 版本表按库隔离 ⇒ 同一版本号在不同库各自记录，互不干扰。
- 运维口径：升级后对已有租户库逐个调 `initDb`（幂等）或跑运维脚本；文档写入使用指南 §30。

### 3.10 可观测与诊断

- 日志（结构化前缀固定，便于 grep）：`[migration] {version} ok|FAIL|SKIP {ms} reason=...`、`[migration] 库={configId} ...`。
- 健康面：升级件失败⇒ `/health` 不就绪（见 D2），错误信息稳定可检索且不泄露堆栈（沿用异常中间件口径）。
- 只读诊断 SQL（写进运维手册）：`SELECT "Version","Description","Baseline","AppliedAt","DurationMs" FROM sys_migration ORDER BY "Version";`
- 可选 CLI（D6）：`dotnet run -- --migrate-only` / `--migrate-status`，用于部署窗口先升级再放流量；不做则不阻塞本次实施。

## 5. 验收与测试计划

1. **零库档**（无 PG）：脚本扫描排序（含重复版本 fail-loud）、checksum 计算稳定、Options 开关禁用时零执行、`AffectedTables` 为空拒绝执行、帮助类条件生成（可用表达式/反射断言）。
2. **真实 PG**：版本表唯一约束；单脚本事务失败 ⇒ 数据回滚＋无版本行＋下次启动重试成功；已应用脚本 checksum 改动 ⇒ fail-loud；双实例并发（真实 Redis 锁）⇒ 只执行一次；基线登记（空库/存量库两态）；表级快照生成与幂等复用。
3. **升级演练**：造 `sys_config` 探针行 + 一个只改该行的脚本 ⇒ 备份快照存在、改后版本行正确、人为让脚本失败验证回滚与备份恢复；finally 清理探针（备份表保留由人工确认后删）。
4. **回归**：严格门 0W/0E＋全量 `dotnet test`；不改 `.json` 配置、不新增门控脚本（红线⑤）。
5. **真机**：测试版 5090 部署后，版本表落 baseline 行；用一个"无操作脚本"验证执行链，再撤（避免在测试版跑真实数据演进，真实脚本候发版窗口）。

## 6. 首批升级件候选（实施批次 C，需逐个评审）

> 原则：每个脚本都写成"仅当库值仍等于旧默认值才改"；能否自动改写，需先跑只读审计确认存量库现状。

1. `20261101_01__menu_tree_regroup`：把 2026-09-30 前菜单树（24 菜单直挂 10001）重挂到六顶级目录，仅当行 Pid/OrderNo 仍等于旧默认值。
2. `20261101_02__role_menu_grant_backfill`：按新菜单集补齐系统管理员授权行（仅缺行插入）。
3. `20261101_03__sys_config_defaults`：配置默认值演进（如未来改 `sys_otp_enabled` 缺省策略），仅当值等于旧默认值才更新。
4. `20261101_04__seed_row_normalize`：历史种子行字段规范化（如 `SysOrg.Remark` 旧 schema 非空遗留），按现状审计后决定是否做。
5. `20261101_05__sysuser_seed_selfheal`：把命令式种子 `SysUserSeed` 里的存量自愈（`AccountType` 只升 999、`TenantId` 补默认值）迁成升级件。第一步未动它（它不是 runner 的 upsert 通道，且是"只升不降/只补空"的自愈语义），但它仍是**启动期隐式写**，按"结构演进走升级件"的终裁应归并进来。

## 7. 待评审决策点（评审请逐条拍板）

| 编号 | 决策点 | 备选 | 建议 |
|---|---|---|---|
| D1 | 执行位置 | 种子前 / 种子后 | **种子后**（升级件可引用本版本新增种子行） |
| D2 | 失败语义 | 与现有启动降级一致（服务监听、/health 可用）/ **fail-fast 中止启动** | **fail-fast**：升级件半完成态下继续对外服务风险更高；与现有"外部依赖不可用降级"不同类，需显式实现（进程退出或 /health 不就绪＋拒绝流量） |
| D3 | 备份策略 | A 整库 pg_dump / **B 表级快照** / C JSON | **B 为主**，A 写入发版运维手册 |
| D4 | 基线策略 | **首启登记基线、不回放历史脚本** / 历史脚本全量回放 | **登记基线**＋上线前只读审计（§3.7），回放方案风险不可控 |
| D5 | 并发第二道闸 | 仅复用启动 Redis 锁 / 另加 PG advisory lock | 加 PG `pg_advisory_xact_lock`（锁失效时的兜底；成本一行 SQL） |
| D6 | 是否需要 CLI/独立升级命令 | 只要启动期自动执行 / 加 `--migrate-only`、`--migrate-status` | 首批只做启动期自动＋只读状态 SQL；CLI 后补（避免范围膨胀） |
| D7 | 脚本载体 | **C# 类型** / 运行时 SQL 文件 | **C# 类型**（类型安全、可分支、无文件部署风险） |

## 8. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 基线登记掩盖存量库真实差异 | 上线前只读审计＋基线行记录 git sha；首批脚本另带"现状自检"日志 |
| 备份表占用磁盘/被误当业务表 | 统一 `_bak_` 前缀＋运维清理脚本；`[IgnoreTable]` 语义上不参与任意扫描（备份表不是实体） |
| 升级件失败导致服务起不来（fail-fast） | 部署窗口先跑升级、备份在手可快速恢复；/health 与日志给可检索归因（§3.10） |
| 多实例滚动部署时旧实例仍在跑旧代码 | 版本表唯一索引＋checksum：旧实例启动看到"未来版本"⇒ 记 WARNING 不执行（规则待 D5 评审时细化：**版本表存在高于本代码的版本 ⇒ 拒绝启动**，防新旧代码交叉写库） |
| 升级件变成"新的隐式魔法" | 强约束：每版本一份脚本、必须在 CHANGELOG/运维手册点名、禁在种子 upsert 里做演进；审计 SQL 可随时看全量版本 |
