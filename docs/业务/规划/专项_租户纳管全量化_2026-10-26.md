## 3. 日志表历史行的处置（B 无法回避的语义决定）

过滤谓词是 `TenantId == 当前租户`，NULL 恒不命中 ⇒ 历史日志若填 `DefaultTenantId`，效果＝**默认租户看得见全部历史、其他租户一律看不到自己的历史**（可见性错乱）；若留 NULL，效果＝**历史日志对所有人不可见（超管除外）**。
**本会话建议**：日志四表历史行**留 NULL＋文档标注"纳管前历史不参与租户过滤，仅超管可查"**，写侧自纳管之日起必填；不伪造归属（伪造比缺失更坏）。**此项需你点头，未点头前日志四表不动。**

## 4. 契约冲突（B 会推翻的既定决定，均为代码注释自陈）

1. **`sys_log_op`**：`SysLogOp.cs:13`「继承 EntityBase 而非 EntityTenant（**契约口径**）：操作日志**全租户可见**（运维审计视角），不参与租户过滤」。⇒ 纳管＝**撤销"运维审计全租户可见"设计**。旁证不一致已存在：`SysLogLogin.cs:12` 明写「WHY 继承 EntityTenant（契约口径，与 **SysLogOp 的 EntityBase 不同**）」，`SysLogMsg` 也是 EntityTenant ⇒ **同族日志表两种口径并存**，B 会把它统一（这是 B 的主要收益之一）。
2. **`sys_config`**：全局配置若按行隔离 ⇒ **平台默认配置对所有租户消失**（表现为"配置项凭空不见"，不是报错，难发现）。必须配全局哨兵＋查询侧豁免才可上线。
3. **`sys_role_table`**：`SysRoleTable.cs:16` 自称"与 `SysRoleMenu`/`SysRoleApi`/`SysRoleOrg` 同口径——角色授权是平台级配置"，但那三张**现在都是 `EntityTenant`** ⇒ **该注释已过期**，本表是族内唯一漏网者。⇒ 此表纳管是**补齐一致性**，无契约冲突（反而是修复）。
4. **`sys_file`（连带）**：`SysFile.cs:10`「按 task_012 要求不归属租户（无需租户行级过滤）」。B 若覆盖 `sys_file_content`（第 5 项）实际等于间接推翻它 ⇒ **须一并纳管 `sys_file` 并把 task_012 的旧决定显式作废**，否则出现"正文隔离、外壳不隔离"的半吊子状态。

## 5. 隐藏工作量（不是"加个列"就完）

`src/Core/SqlSugar/SchemaIntegrityInitializer.cs:54-55` 规定：**EntityTenant 表的唯一键必须含 `TenantId`（租户内唯一）；EntityBase 表全局唯一**。⇒ 11 张表**每一张的既有唯一索引都要复核**是否需改为"租户内唯一"：改＝额外 DDL（删旧索引＋建含 TenantId 的新索引），不改＝跨租户撞键（A 租户存了 X，B 租户就存不进）。**此项未计入任何"1 列 DDL"的估算，是本专项最大的低估风险。**

```sql
-- 批 1-① sys_role_table（0 行，无回填风险）
ALTER TABLE sys_role_table ADD COLUMN "TenantId" bigint NOT NULL DEFAULT 1300000000001;
-- 唯一键纳入 TenantId：跨租户同名同键配置不再互撞（否则 A 租户建过的键，B 租户建不了）
DROP INDEX i_sys_role_table;
-- ⚠ 行为变更（须显式批准）：补 WHERE "IsDelete"=false 使软删行不占键位，与仓内其它唯一键同口径。

CREATE UNIQUE INDEX i_sys_role_table ON sys_role_table ("TenantId", "RoleId", "TableName", "ColumnName")
  WHERE "IsDelete" = false;

-- 批 1-② sys_user_otp（2 行，2/2 可回填）
ALTER TABLE sys_user_otp ADD COLUMN "TenantId" bigint NOT NULL DEFAULT 1300000000001;
UPDATE sys_user_otp o SET "TenantId" = u."TenantId" FROM sys_user u WHERE u.id = o."UserId";

-- 批 1-③ sys_notice_user（740 行，736 行孤儿行按 §9 口径处理）
ALTER TABLE sys_notice_user ADD COLUMN "TenantId" bigint NOT NULL DEFAULT 1300000000001;
UPDATE sys_notice_user n
   SET "TenantId" = COALESCE(nt."TenantId", u."TenantId", n."TenantId")

  LEFT JOIN sys_notice nt ON nt.id = n."NoticeId"

```

**一次批准不等于 11 张表批准**（红线① 逐批请示）——本草案只覆盖批 1 的 3 张表。

### 11.2 ⚠ 关键口径：**`AccessKey` 唯一键不得纳入 `TenantId`**
直觉做法（照抄批 1 的"唯一键纳入 TenantId"）在**本表是错的**：
- 鉴权入口是**凭 key 找身份**——`SysOpenAccessService.cs:163` `GetFirstAsync(u => u.AccessKey == accessKey)` 与 `:179`（按 secret）。**若 key 只在租户内唯一，鉴权时无法定位唯一身份**（两个租户同一 key ⇒ 拿错租户的身份，等于跨租户冒名）。
- ⇒ 正确形态＝**`TenantId` 只作查询过滤列，`AccessKey` 唯一键保持全局**（现网实证：**无跨租户重复 key**，保持全局唯一不产生迁移冲突）。

### 11.3 ⚠ 由 11.2 派生的**必改代码**（本专项落地批 2 时同批处理，现在只登记）
一旦 `SysOpenAccess` 实现 `ITenantIdFilter`，仓储查询会自动带租户过滤 ⇒
1. **`AddAsync` 里的 `IsAnyAsync(u => u.AccessKey == input.AccessKey)` 会退化成"仅当前租户内查重"**，而唯一约束是**全局**的 ⇒ 撞上别的租户已占用的 key 时，**应用层漏报 `open_access.access_key_exists`，改由数据库唯一索引抛原始异常**（用户看到 500 而不是可检索的业务错误码）。
   **⇒ 该查重必须改 `IgnoreTenant`**，与我在批 ⑫（`2f56726`）里给绑定校验用 `IgnoreTenant<SysUser>()` 是**同一个道理的第二次出现**：**"全局唯一的东西，校验不能站在租户视角做"**。
2. 认证路径两处取数（`:163`/`:179`）**必须钉住"跨租户可取"**：认证发生在 `PermissionMiddleware` 加过滤器**之前**，理论上不受影响——但这是**推断**（[假设]），批 2 必须用测试证死，不能靠时序推定。

### 11.4 批 2 结论
**代价**＝1 次加列 DDL（0 活跃行）＋ **1 处必改代码**（11.3-1）＋ **1 条必新增测试**（11.3-2）；顺带可登记清理 1 个冗余索引。
**风险提示**：本表是**鉴权链**上的表，纳管失败的后果不是"数据串了"而是"**开放接口整体认证不过**" ⇒ 批 2 属本专项 6 批里**风险最高**的一批，即便只有 8 行软删数据，也**不得与批 1 合并执行**。
