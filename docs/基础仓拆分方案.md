# 基础仓拆分方案（开发文档与业务框架解耦）

> 状态：已执行远端拆分（2026-10-21）
> 目标：让业务项目 fork 的 `BaseAdminCore` 只包含框架代码与公共文档；内部立项、研究、验收、计划、环境与部署操作文档移出到私有文档仓。
> 原则：**代码只保留一份真源**；不建立两个都能改代码的仓。

## 一、结论

采用「基础代码仓 + 私有文档仓」：

| 仓 | 可见性 | 内容 | 角色 |
|---|---|---|---|
| `BaseAdminCore` | 业务方可见 | `src/`、`web/`、`thirdparty/`、构建配置、公共框架文档 | 唯一代码真源；业务 fork 的 upstream |
| `BaseAdminCore-Docs` | 私有 | `CLAUDE.md`、`plans/`、`docs/archive/`、`docs/研究/`、`docs/业务/`、差距/立项/环境/推进等过程文档 | 开发过程、审计与运维资料 |

框架开发仍在 `BaseAdminCore` 进行；内部文档不再回流到基础仓。业务方 fork 后只看到框架本身。

不采用「开发仓 + 基础仓」两个代码仓：双份代码必然漂移，合并成本远高于一次性剥离文档。

## 四、导出方式

基础仓由脚本从开发仓当前 `HEAD` 按白名单生成，避免手工复制造成遗漏。

- 白名单：`scripts/base-export/allowlist.txt`
- 导出脚本：`scripts/base-export/export-base.ps1`
- 清洗脚本：`scripts/base-export/sanitize.ps1`
- 校验脚本：`scripts/base-export/verify-base.ps1`
- README 模板：`scripts/base-export/templates/`

两种模式：

1. `Snapshot`（默认/推荐）：按白名单复制当前 `HEAD`，生成单个初始提交；不保留开发历史，避免提交信息中的内部任务、主机与批次信息泄露。
2. `FilterHistory`：使用 `git filter-repo` 按路径重写历史；仅适合已确认提交信息与作者信息可公开的场景。实测开发期提交信息含内部主机/任务记录，基础仓发布不采用。

无论哪种模式，导出后都会：

1. 用模板覆盖 `README.md`、`docs/README.md`；
2. 对公共文档/代码注释做敏感词与内部路径清洗；
3. 运行校验：必需文件存在、禁止路径不存在、禁止词零命中。

## 五、执行步骤（已执行）

### 5.1 冻结与备份

```powershell
git tag pre-base-split-2026-10-21
git push origin pre-base-split-2026-10-21
```

### 5.2 迁移内部文档到私有仓

```powershell
# 在临时目录用 filter-repo 只保留内部文档历史
git clone --no-hardlinks <当前仓> BaseAdminCore-Docs
cd BaseAdminCore-Docs
git filter-repo --force --paths docs/archive docs/研究 docs/业务 plans CLAUDE.md `
  docs/框架差距清单.md docs/立项.md docs/环境管理.md `
  docs/自主推进_BaseAdminCore.md docs/sqlsugar升级评估-G7G9.md `
  docs/上送_立项件阶段门历史化_2026-10-17.md docs/框架功能清单.md
```

推送前补一份文档仓 `README.md`，说明这是内部仓、对应基础仓版本与目录约定。

### 5.3 生成基础仓

```powershell
# 建议在独立目录执行，不覆盖当前工作区
.\scripts\base-export\export-base.ps1 `
  -Source . `
  -Dest ..\BaseAdminCore-base `
  -Mode Snapshot `
  -Remote <新基础仓地址>
```

确认输出零异常后，再执行 `-Push` 或手工推送。

### 5.4 远端切换

1. Gitea 将现仓改名为 `BaseAdminCore-Dev`（保留内部文档与完整历史），或归档为只读审计仓。
2. 新建 `BaseAdminCore`，接收导出结果。
3. 更新 IntelCore 等下游的 `upstream` 地址。
4. 下游接入新 `upstream`：新业务仓直接 fork 新基础仓；已有业务仓保留旧历史，按文件差异逐步合并，不强行 rebase 不相交历史。

## 六、清理欠账

基础仓导出后，以下内容仍需人工复核：

1. **代码注释悬空**：约 15 处引用 `docs/研究/...`、`docs/框架差距清单.md`。导出脚本会做文本替换，但建议逐条确认语义是否仍通顺。
2. **公共文档内部引用**：`docs/框架索引.md`、`docs/框架使用指南.md`、`docs/框架开发参考手册.md`、`docs/baseadmin设计精华参考.md` 中存在 `MainWorkspace`、`huluyeye`、`Admin@123`、`docs/研究` 等引用；导出脚本会清洗，需人工复核敏感信息零残留。
3. **默认密码**：公共文档不得出现真实初始密码；清洗统一改为开发占位密码 `ChangeMe@123`，首次登录后立即修改。
4. **许可证**：当前仓无 `LICENSE`，业务 fork 前必须由维护者确定。
5. **版本说明**：建议基础仓每次发布打 tag，并在 `CHANGELOG.md` 记录框架级变更。

## 七、回滚

- 执行前已打 tag，可随时从 tag 恢复。
- 远端改名/新建前先导出 Gitea 备份。
- 本方案不删除当前工作区任何文件；内部文档迁移在新克隆中完成，原仓保留。
