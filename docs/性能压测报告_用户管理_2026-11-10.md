# 性能压测报告：用户管理模块（`/api/sysUser/page`）

- 日期：2026-11-10
- 压测工具：k6 v2.3.0（GrafanaLabs.k6，winget 安装）
- 压测对象：`GET /api/sysUser/page`（用户管理分页列表）
- 脚本：`scripts/load-user-page.js`、`scripts/get-token.ps1`

---

## 1. 测试目标指标（用户指定）

| 指标 | 目标值 |
|---|---|
| 并发数（concurrency） | **100** |
| 吞吐（QPS） | **300** |
| P95 延迟 | **≤ 200ms** |
| 失败率 | < 1%（附加约束，压测脚本默认断言） |

## 2. 测试环境与拓扑

```
k6(本机) --HTTP--> ASP.NET Core 后端(本机 :5090, .NET 10)
                        ├── PostgreSQL 180.76.244.101:5432/huluyeye_admin（公网远程库, RTT 高）
                        └── Redis 127.0.0.1:6379（本机）
```

- 后端鉴权：JWT（`AccountType=999` 超管，`sysUser/page` 按钮权限自动放行）。
- 获取 token 采用双因子 OTP 两阶段登录，见 `scripts/get-token.ps1`。
- 被测业务库为公网远程 PostgreSQL（`Host=180.76.244.101`），本地 k6 与后端同机。

## 3. 测试方法

k6 提供两种互补场景（`load-user-page.js` 通过 `-e MODE=` 切换）：

| 模式 | executor | 含义 | 用途 |
|---|---|---|---|
| `arrival`（默认） | `constant-arrival-rate` | 强制 **300 请求/秒**到达率，并发上限 100 | 检验"能否接住 300 QPS 的持续压力"；接不住会表现为 `dropped_iterations` 上升 |
| `vus` | `constant-vus` | 固定 **100 个并发真实用户**，不加压不丢请求 | 最贴合"并发数 100"，测出系统在该并发下的真实吞吐与 P95 |

公共阈值断言：`http_req_duration p(95)<=200`、`http_req_failed rate<0.01`。

### 复现命令

```powershell
# 1) 取 JWT（两阶段 OTP 登录，提示时输入验证器当前 6 位动态码）
.\scripts\get-token.ps1

# 2) 全天候压测（固定 100 并发，60s）
k6 run -e TOKEN="<JWT>" -e MODE=vus  -e DURATION=60s scripts/load-user-page.js

# 3) 恒压到 300 QPS 探顶（可再调 -e RATE= / -e DURATION=）
k6 run -e TOKEN="<JWT>" -e MODE=arrival -e RATE=300 -e DURATION=60s scripts/load-user-page.js
```

> token 有效期约 8 小时；压测中若出现 401，用 `get-token.ps1` 重新取。

## 5. 阈值判定（结论：**未达标**）

- 失败率 ✅（0%，接口本身功能正确）；P95 ❌、吞吐 ❌。
- **用户管理列表接口在 100 并发下不满足 300 QPS / 200ms P95 目标。**

## 6. 根因分析

关键证据：

1. **单点性能正常**：无并发时该接口中位数约 **120ms**，查询本身不慢。
2. **仅高并发时崩**：后端 `OpLogFilter` 慢请求告警刷出大量 `GET /api/sysUser/page ElapsedMs=4.4~9.6s`；`avg=4.97s ≫ med=431ms`，是**少数请求被长时间排队**而非整体变慢，典型资源饱和特征。
3. **连接池与并发撞车**：运行时连接串未设 `Maximum Pool Size` → Npgsql 默认 **100 槽**，恰与并发 100 相同。分页请求需跨**公网远程库**多次往返（主查询 + Count + 数据权限过滤），进程内 op_log 事件异步落库**还挤同一批连接** → 100 并发瞬间填满池 → 后续请求等空闲连接，最长排到 **15s（Npgsql 默认连接超时）**，与 P95≈16.6s 高度吻合。
4. 失败率 0% 但最终都成功，是因为连接超时后即被释放复用，请求"拖着超时跑完"，故无报错。

**一句话根因**：`远程高 RTT 的 PG + 默认 100 连接池 + 每请求多 DB 往返 + op_log 并发抢连接`，在 100 并发下连接池耗尽 → 延迟被"等连接"拖到十几秒，吞吐坍缩为 ~18 QPS。

## 7. 改进建议（按投入产出排序）

1. **立即可验**：连接串追加 `Maximum Pool Size=400`，并设 `Timeout=5`（等不到连接的请求快速失败而非拖着超时）。前提是瓶颈在"连接数"而非 DB 侧吞吐；改后重测验证。
2. **减少 DB 往返**：分页查询合并为单次 SQL（SELECT + COUNT 同批），数据权限过滤避免重复子查询扫表。
3. **日志解耦**：op_log 走独立日志库（配置里 `log` ConfigId 默认注释），把审计写库流量从主库剥出，减轻与主库的争用。
4. **架构上限**：单台公网远程 PG（RTT 高）在 300 QPS / 200ms P95 下较难稳定。若为硬指标，需 DBA 侧补索引 + 应用与库同机房/内网部署。
