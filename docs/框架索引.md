### 7. 事件总线（Core/EventBus，task_014）

发布即入队（`IEventPublisher.PublishAsync<T>(eventName, payload)`；Channel 有界容量 1000，满则等待背压不丢数据）→ `EventBus`（BackgroundService，单例）异步执行订阅（主流程不等待）→ 执行委托 `IEventHandlerExecutor`（批 S：默认 `RetryEventHandlerExecutor`——`sys_log_event` 审计表状态机 Running→Success/Retry→Error＋精细重试按订阅特性 NumRetries/RetryTimeout/ExceptionTypes 白名单、缺省回落全局 ≤2/1s＋`[SuppressMonitor]` 审计 opt-out；审计写失败/重试耗尽仅告警不上抛，不阻断队列）。订阅者 = `IEventSubscriber` 实现＋**方法级** `[EventSubscribe(eventName)]`（启动反射扫描，新增订阅零注册代码）。当前三订阅：`OpLogSubscriber`（"op_log" → SysLogOp 异步落库，`[LogTable]` 路由日志库）/`MsgLogSubscriber`（批 G 4.8："msg_log" → SysLogMsg 异步落库；订阅者 `[Service(ServiceType=typeof(MsgLogSubscriber))]` 显式具体类型注册——总线按类型从作用域解析）/**`ExLogSubscriber`（批 I 5.1："ex_log" → SysLogEx 异步落库；同 OpLogSubscriber 范式：Transient `[Service(ServiceType=具体类)]`＋`[EventSubscribe]`＋失败重试≤2 不回流）**。

**Redis 双通道（批 AC 5.6 集群扩展）**：本地通道不变（发布即入队/有界背压/订阅者反射扫描/执行器重试审计全部沿用）。双通道 = 本地通道＋跨实例通道，配置三项：`EventBus:EnableRedis`（bool，缺省 **false**=纯本地内存通道）/`EventBus:Channel`（缺省 `admincore:eventbus`，同集群各实例须一致）/`EventBus:CrossInstanceEvents`（**逗号分隔事件名白名单，缺省空**）。语义：发布侧本地入队后，仅当「开关开＋有 Redis 连接＋事件名在白名单内」才向 Redis `PUBLISH` 一份 JSON 信封（事件名/事件 Id/来源实例标识/载荷 JSON）——**广播失败只 LogWarning，不影响本进程内执行**；接收侧收其它实例消息 → 按**订阅方法参数类型**反序列化还原载荷（每个订阅者各自还原，还原失败仅告警跳过该订阅者，不阻断队列）→ 投本地队列执行。四条硬口径：① **自回环丢弃**（信封来源实例标识 `机器名:进程号:GUID` ＝本实例 → 丢弃，否则自己广播的事件会被自己再执行一遍）② **白名单发布侧与接收侧同判据**（防手工 PUBLISH 注入旁路）③ 队列满时跨实例副本用 `TryWrite` 丢弃＋告警（Redis 回调是同步签名，等待背压会挂住回调线程；本进程内消息仍走 `WriteAsync` 背压不丢）④ **白名单为空 ⇒ 双通道等价纯本地**（零风险）。**WHY 白名单而非"开启即全广播"**：本仓内建订阅者 OpLog/ExLog/MsgLog 的语义是**本实例写本实例的库**（审计行归属"谁处理的请求"），把 op_log/ex_log/msg_log 广播出去会让每个实例各执行一次订阅 → **审计行重复落库**；跨实例投递只对**显式登记**的事件生效（典型用途：缓存失效/配置变更/在线用户跨实例通知）。**降级**：开关开但容器无 `IConnectionMultiplexer`（如 Memory 缓存回落）→ `LogWarning` 降级纯本地；`Subscribe` 失败 → `LogError` 降级纯本地（不阻断宿主启动）。**零新依赖**：复用缓存已引的 `StackExchange.Redis`（约定 #11 复用优先）；Pub/Sub **无持久化**（离线实例丢消息）属集群扩展期口径，持久化投递（Stream/MQ）按需另立。使用范式见使用指南 §31。

**内建跨实例事件（批 AU/AV/BC）**：框架内建事件名由 `EventBusEvents` 收口，并由 `CrossInstanceBuiltIns` 清单登记（当前 **3** 个：`online_force_offline` 强踢／`online_push` 在线推送／`sqlsugar_cache_invalidate` 二级缓存失效）；守卫据此**逐项**判定并告警（清单是守卫与文档的唯一数据源）；**白名单仍是唯一准入闸**（双侧同判据不变），本批只是把"内建可用事件"显式登记，并加了构造期守卫——开了双通道却没登记该事件时启动即告警（否则现象是"踢人接口 200 但用户在别的实例上不掉线"，静默失效最难查）。

### 9. 定时任务（Core/Job，task_108，Furion.Schedule 原生替代）

- **注册**：任务 = `IJob` 实现＋`[JobName("name")]`（调度名）＋`[Service]`（DI）——JobScheduler 启动反射扫描双程序集取 `[JobName]` 类型（重名即抛）。服务经 `IJobScheduler`（Singleton，`[Service(ServiceType=typeof(IJobScheduler))]`＋AddAutoServices 补注册 IHostedService）零改 Program.cs。
- **调度循环**（BackgroundService 常驻，5s 粒度）：启动预载 SysJobDetail 数据库行（重启恢复；DB 不可达不阻塞宿主，每轮重试自愈）→ 每轮检查到期（`Interval` 秒到点，LastRunTime 以开始时刻计）→ fire-and-forget 触发执行（循环不等待执行完成）→ 每 60s（12 轮）刷新数据库快照（管理侧 启用/禁用/间隔 变更 1 分钟内免重启热生效）。
- **防重入**（单机口径）：触发前经 `ICacheService.IncrementAsync` 原子取锁 `sys_job:{name}`（首增者持锁，>1 跳过；执行完 finally `RemoveAsync` 释放；TTL 30min 仅防进程异常后锁残留）。RunNow 与调度触发同一条 `FireAsync` 路径、同口径（上一轮未完成 → 拒绝）。**批 AK 补（重复触发窗口）**：这把锁只回答「现在有没有人在跑」，不回答「这一轮是不是已经跑过了」——内存快照 60s 才重载 ⇒ 执行完锁一释放，下个 tick 照样判到期照样取锁重复执行（实测 5.1s 窗口 11 次）⇒ 取锁后须在**锁内**以共享基准 `KeyJobLast` 复检（见机制 28／指南 §42.6）。**批 AJ 集群扩展见机制 28**（执行期锁续租／节点心跳／`TargetNode` 归属实例／`KeyJobRunning` 运行中登记，使用范式见指南 §42）——Redis 档下本锁**本就跨实例**（这点原本是对的），但 **TTL 只是「防残留」不是「执行超时上限」**：**长任务必须让续租生效**，否则超 TTL 会被另一实例**静默重复执行**。
- **DB 串行**：共享单例 SqlSugarScope 同一实例并发不安全（并发探针实证，见差距清单 G7）——调度器自身三类 DB 操作（后台预载/任务执行/RunNow）经 `_dbSerial` SemaphoreSlim 互斥。**通用并发契约与 `CopyNew()` 用法见使用指南 §59**（调度器串行化只是其中一种"单一写者"路线）。
- **失败隔离**：任务执行异常仅 LogError＋不退出调度器；LastRunTime 已在触发点更新，下次到点照常。
- **内置任务**：`CleanSysLogJob`（`[JobName("clean_sys_log")]`）清 SysLogOp/SysLogLogin/SysLogDiff（批 X）/SysLogHttp（批 AD）/SysLogEx/SysLogEvent **六表**同保留期超期行，保留天数 `SysJob:LogRetentionDays`（缺省 30）；`DeletePhysicalByAsync` 物理删。

### 11. 开放接口认证（批 E：[OpenApi] 先行认证＋双 scheme）

- **端点标注**：`[OpenApi]`（Core/Attributes，可继承方法标记）＋`[Authorize(AuthenticationSchemes = "Signature,ApiKey")]`（或含 "Bearer,..." 的 OrJwt 变体）。`[OpenApi]` 端点**必须**声明 `AuthenticationSchemes`，缺 → 401（防裸开放端点）

- **Claims 与 JWT 同构**＝绑定用户身份：UserId/TenantId/Account/RealName/AccountType/TokenVersion/**OrgId（批 E 新增 `JwtClaimNames.OrgId`）**；开放接口请求经绑定用户运行 → **AOP 审计/租户过滤/机构数据范围全生效**（`TokenVersion` 取绑定用户实时值——参照写死 "1" 是疏漏，已修）
- **密钥生命周期**：AccessSecret 服务端生成（`CreateSecret()`＝16B GUID Base64 截末 2 位＝22 字符），仅 Add/ResetSecret 响应一次性返回；分页 Out 不回显；Update 仅可改绑定

### 18. ORM 分表（批 AC：3.1 收尾）

- **建表入口**：`SqlSugarSetup.InitTables`／`InitTenantTables` 在「按实体特性选库分组」之后**再按是否分表分组**——普通实体 `conn.CodeFirst.InitTables(normalTypes)`，分表实体 `conn.CodeFirst.SplitTables().InitTables(splitTypes)`（**WHY 必须分开**：分表表名是按时间模板生成的通配名，混进普通 `InitTables` 会按模板名建一张错表——表名里带 `{year}{month}` 字面量）；判定单点 `SqlSugarSetup.IsSplitTableEntity(Type)`（`internal`，判 SqlSugar `[SplitTable]` 特性）
- **列名自愈跳过**：`HealColumnCase` 跳过分表实体——分表表名是含时间模板的通配名，按模板名查 `information_schema` **恒查不到**；子表列名一致性由 `CodeFirst.SplitTables().InitTables` 建表时按声明列名保证
- **查询入口**：`ISqlSugarRepository<T>.AsSplitQueryable()`——按分表策略展开查询（**跨子表 UNION**），返回 `ISugarQueryable<T>`，其后过滤/排序/分页照常链式追加
- **写入入口**：`ISqlSugarRepository<T>.InsertSplitAsync(T entity)`——按实体时间字段路由到对应子表，**子表不存在自动创建**；审计字段/雪花主键仍由 AOP 填充（与普通 Insert 同口径）
- **边界（显式暴露，不静默退化）**：非分表实体调用 `AsSplitQueryable()`／`InsertSplitAsync()` → **SqlSugar 直接抛异常**（不回落单表查询/写入）；能力分支用 `SqlSugarRepository<T>.IsSplitTableEntity`（静态属性，转发 `SqlSugarSetup.IsSplitTableEntity`）
- **选库口径不变**：仓储/建表/AOP 均按既有口径走 `Context`（构造时按 `[Tenant]/[LogTable]/[SysTable]` 选定的连接）——分表只改「表名怎么算」，不改「库怎么选」（多租户库级隔离与分表正交，见机制 5/17）
- **实体约定（实测口径，SqlSugar 5.1.4.221）**：`[SplitTable(SplitType.Month)]`（类级）＋分表时间字段贴 `[SplitField]`（属性级，须 DateTime/DateTimeOffset）；**表名必须同时含 `{year}{month}{day}` 三个占位符**（规范形态 `前缀_{year}{month}{day}`）——缺任一即建表抛 `SqlSugarException`（「分表表名需要占位符 {year}」），如 `ac_split_probe_{year}{month}{day}`；Month 粒度下 `day` 恒为 `01`（日期归一到月首），实测子表 `ac_split_probe_20260901`/`ac_split_probe_20260801`。分表字段为 null/`DateTime.MinValue` 或不标 `[SplitField]` → 回落 `db.GetDate()`（写当前期）。分表实体禁 `IsIdentity=true`（雪花主键可用）。实测见 `src/Test/BatchACSplitTableTest`

### 21. 队列与分布式锁原语（批 AF：5.10 最小集）

- **入口**：`ICacheService` 新增 **6 原语**（零新依赖，沿用既有 `StackExchange.Redis`/`IMemoryCache` 双实现）——`LockTakeAsync(key, token, expiry)`（Redis=`SET key token NX PX ms`）/`LockReleaseAsync(key, token)`（Redis=**Lua 原子「比对 token＋DEL」**；**WHY 比对**：不比对就会把"自己超时后、别人已拿到"的锁删掉，互斥静默失效）/`ListPushAsync(key, value, leftPush=true)`（true=左入，配右出=FIFO）/`ListBlockingPopAsync(key, timeout)`（Redis=**BRPOP**，超时返回 null；Memory=**50ms 轮询**）/`ListLengthAsync`（积压量）/`ListRangeAsync(key, start, stop)`（排障取队头/全量）
- **键约定**：`CacheConst.KeyQueuePrefix = "queue:"`——**只给约定不强制**（框架不擅自改写业务键；调用方自行拼完整键，如 `queue:order:dispatch`）；与 eventbus 频道（6380 实例的 `admincore:eventbus`）/业务侧（如 Python）自有键**共用同一 Redis 实例**时靠前缀隔离

- **归属校验位置（扫描期跳过）**：`SysJobDetail.TargetNode`（string? 128）空=任意实例；非空=**仅 `NodeTag` 匹配（不分大小写）的实例执行**，其余实例在**扫描期直接 `continue`——不加锁、不占位、不写运行中登记**（跳过 ≠ 持锁）；代价是**标签写错＝集群内无人执行且不报错不告警**
- **端点字段**：`isAlive`＝读侧心跳超期判定、`isSelf`＝是否本进程（运维对照用），僵尸节点在出口前已过滤；数据为当轮快照（心跳粒度＝调度轮询，缺省 5s），**非推送**
- **实现档硬约束**：**Memory 档下节点表与锁都不跨进程** ⇒ **多实例部署必须 Redis 档**（同机制 21 口径）；心跳/续租/登记失败一律**只告警不阻断调度**（可观测性件不得让任务不跑）
- **重复触发防护（批 AK 追加，单实例与多实例同一条路）**：防重入锁只保证「不同时跑」，不保证「同一轮不重复跑」——`IsDue` 读的内存快照每 12 tick（60s）才整表重载，任务执行完、锁释放后每个 tick 都仍判到期并重复执行（批 AK 实测 5.1s 窗口 **11 次**，期望 1；`BatchAKJobRepeatTriggerTest` 判据①）。修复口径＝**共享权威「上次触发时刻」＋锁内复检**：新键 `KeyJobLast`（`sys_job_last:{name}`，值＝DateTime）；`FireAsync` 取到锁（`lockValue==1`）后在**锁内** `ConfirmDueBySharedLastAsync` 复检——键不存在时用内存快照值（＝DB 预载值）兜底并视为权威；未到点 ⇒ **就地 `RemoveAsync` 释放锁**＋把内存快照对齐权威值＋不执行；到点 ⇒ **先 `SetAsync` 写共享基准（TTL＝`max(1 小时, 2×Interval)`，见 `LastTtlFor`）、再回写内存快照**（`WriteSnapshotLastRun`：record 不可变 ⇒ 复制整表换新引用，沿用「写侧整体替换、读侧免锁」；同名任务由锁保证单跑 ⇒ 与 60s 刷新并发是 last-write-wins 且两侧写的是同一时刻，可接受），然后进 `ExecuteTriggeredAsync`。**`finally` 只释放防重入锁、绝不删基准键**（删＝重复触发回归）。`IsDue` 判定式**一字未改**，只降级为快速筛选（快照只会更旧 ⇒ 判「未到点」必然真未到点，不漏触发）。手动 `RunNow` 走 `enforceInterval=false` **跳过复检**（「立即执行、不看 Interval」契约不变），但同样登记本次触发时刻。读/写基准失败一律**保守跳过本轮**＋释放锁（与「锁获取失败即跳过」同口径）。跨实例正确性论证与使用口径见指南 §42.6；判据②（两实例共享真实 Redis＋故意把 DB 基准改回陈旧，逼出共享基准的独立作用，全集群恰 1 次；以仅匹配实例 B 的专属任务反证链路可用防假绿）同在 `BatchAKJobRepeatTriggerTest`

### 31. 站点身份配置化（批 AY：G24，App:Name 单一真源 → 品牌/标题/OTP issuer 贯通运行期）

> 机制入口：`Core/Option/AppOptions.cs`（`App` 节，随 `AddProjectOptions` 绑定）＋`Core/Extensions/ProjectOptionsExtensions.cs` 两处 `PostConfigure`；端点 `Web.Entry/Controllers/AppController.cs`；前端 `web/src/config/brand.ts`＋`web/src/api/app.ts`＋`web/src/main.ts`。

- **补的是什么**：同一份前端产物部署到多套独立服务时分不清"哪个平台"——① 浏览器标签/登录页品牌来自**构建期** Vite 变量（`VITE_BRAND_*`），换名要重新构建；② OTP 认证器条目名（otpauth issuer）与站点名各配各的，容易只改一处。本批把 `App:Name` 立为**唯一真源**：改一个配置（或 env `App__Name`）三处同步变化。
- **回落链（照写）**：`App:Name` → `App:FullName` 空则回落 `Name` → `App:TitleSuffix` 空则**留 null 交前端兜底**；`Otp:Issuer` 空则回落 `App:Name`（显式 `Otp:Issuer`/env `Otp__Issuer` **优先**，兼容既有部署）；`App:Name` 与 `Otp:Issuer` 双空则 `AuthService.BuildOtpauthUri` 既有兜底文案收尾（**绝不产生空 issuer 的断 URI**——PostConfigure 只做回落、不改消费点逻辑）。
- **前端优先序**：运行期 `GET /api/app/info` > 构建期 `VITE_BRAND_*` > `brand.ts` 字面量缺省。`brand` 是**响应式对象**，拉到身份后侧栏/登录页自动重渲染；浏览器标题由 `applyDocumentTitle()` 在启动时先落构建期值、身份到达后覆盖（**不 await**——后端未就绪不得挡首屏）。
- **"未配置"与"显式空"必须区分（批 AZ）**：`titleSuffix` 在 JSON 层 `null`＝未配置（保留兜底）／`""`＝显式无后缀（标题＝品牌名本身）；`name`/`fullName` 则空串也保留兜底（品牌不允许被置空）。判据在零依赖 `web/src/config/brandIdentity.ts::mergeIdentity`；宿主部署件按"是否设置该变量"判（`${APP_TITLE_SUFFIX+set}`）而非"是否非空"。

### 32. 前端统一交互件（批 BD：需求单「表格加载态与统一交互」2026-09-29，六件套全前端 additive）

- **零破坏**：不碰 `ApiResult`/分页契约/路由/既有 sys 页；菜单种子纯新增（10179 交互模式示例，纯前端零 API 无按钮权限键）。

- ⚠ **两种"删除"口径不同（2026-10-26 实锤，别在注释里写错）**：**服务层** `DeleteAsync`＝**软删**（UPDATE `IsDelete=true`，行留在表内）；**测试清理** `Db.Deleteable<T>()`＝物理删，但**删不到软删行**——框架全局过滤器给 DELETE 自动带 `IsDelete=false`（对照证据：未删的父探针行消失了，服务软删的子行每次运行都留 1 条）。⇒ 结论＝跑测试会留少量软删垃圾，**不影响正确性**（业务查询与带 `WHERE IsDelete=false` 的唯一索引都看不见它），根治＝夹具隔离专项；**不要**为此在测试里用裸 Ado 强删（撞 ADO 事务静态守卫口径）。

- ⚠ **清理兜底口径（2026-10-26 实锤教训，写测试时必看）**：只按"我记下的探针 id"清理**不够**——被测方法的**成功路径**可能造出你未登记 id 的行（本批 `CopyRoleAsync` 在断言失败的那两次运行里各留下 1 条 `探针重复 - copy` 孤儿行，`DisposeAsync` 覆盖不到）。⇒ 探针编码统一带可识别前缀＋本次 GUID 后缀，清理**除按 id 外再按前缀兜底删一次**，并在跑完后用 SQL 核查残留计数。

- **凭据状态纪律（2026-09-28 事故立规）**：e2e/测试**改动真实用户凭据状态**（OTP 绑定、密码、TokenVersion 等）前，必须**先整体备份**（推荐 staging 表 `CREATE TABLE ax_otp_backup AS SELECT * FROM sys_user_otp WHERE ...`）、结束时**原样恢复**（`DELETE` 后 `INSERT ... SELECT * FROM backup`，含 id/时间戳），无备份则恢复为"未绑定/原值"；**实测事故**：回归期自动化两阶段登录会给**真实 admin** 落 OTP 绑定 ⇒ 人工登录"已绑定但码总不对"（本次即由此产生两轮困惑）。**恢复必须「一次性」**：显式恢复与 `trap EXIT` 兜底会各跑一遍，若恢复函数内先 `DELETE` 再 `INSERT` 且**顺手 DROP 了备份表**，第二遍就会「删掉刚恢复的行、INSERT 静默失败」 ⇒ **把用户绑定永久删掉**（2026-09-28 实测踩坑一次，教训立此）；正确写法：恢复函数设 `restored.flag` 闸＋先 `select to_regclass(...) is not null` 校验备份表存在＋**恢复完成后才 DROP 备份表**＋恢复后**断言行数＝备份行数**。**细则本体以本节文字为准**,不以任何脚本存在为前提;当次范例为临时件(`/tmp/ax_e2e.sh`、`/tmp/ax_online_verify.sh`,不入仓、易失)。
